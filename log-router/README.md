# Central Log Analytics router

A .NET 10 isolated Azure Function that consumes **new records exported from one central Log Analytics workspace**, applies origin-specific table/filter policies, and delivers matching records to spoke workspaces through the Logs Ingestion API.

```text
Management workspace -> data export -> dedicated Event Hub -> RouteCentralLogs
  -> origin subscription or tenant + source table + JSON filter
  -> spoke DCR -> spoke custom table
  -> quarantine blob on malformed/unmapped data or failed delivery
```

## What you configure

Edit [routing.json](src/LogRouter/routing.json) for your environment. It contains a tenant-scoped sign-in routing configuration; verify all resource IDs and replace it as appropriate before deployment.

| Property | Meaning |
|---|---|
| `source.subscriptionId` | Management subscription containing the central workspace |
| `source.workspaceResourceId` | Full ARM resource ID of that workspace, **not** the workspace/customer GUID |
| `source.eventHubNamespace`, `eventHubName`, `consumerGroup` | Dedicated export transport; namespace is generated by the deployment script |
| `routes[].name` | Unique, stable route identifier |
| `routes[].originSubscriptionId` | Subscription **represented by the original log**, not the Management subscription |
| `routes[].originTenantId` | Tenant represented by a tenant-scoped log; specify this **instead of** `originSubscriptionId` |
| `routes[].target.subscriptionId` | Subscription hosting the destination workspace |
| `routes[].target.workspaceResourceId` | Full ARM ID of the spoke workspace |
| `routes[].target.dcrResourceId` | ARM ID for a **dedicated router DCR**; deployment creates/replaces it |
| `dcrImmutableId`, `ingestionEndpoint` | Filled automatically from DCR deployment outputs |
| `routes[].tables[]` | Source table, custom destination table, and optional per-route filter |
| `routes[].tables[].targetTable` | Destination table name, including `_CL`; new tables copy the source column names and types |
| `routes[].tables[].streamName` | Must be `Custom-<targetTable>` |
| `subscriptionIdFields`, `tenantIdFields`, `resourceIdFields` | Exact, case-sensitive JSON field paths used to resolve the origin |
| `maxParallelDeliveries` | Maximum concurrent destination groups per invocation; default 8 |

The source is configured once because all routes originate from the central workspace. Add one route for each origin/destination-workspace pair, selecting different tables and filters for each pair. Set exactly one of `originSubscriptionId` or `originTenantId`. Subscription routes resolve the origin from `SubscriptionId`, `_SubscriptionId`, or `/subscriptions/<id>/...` resource IDs by default; tenant routes resolve it from `AADTenantId` or `/tenants/<id>/...` resource IDs. The source workspace subscription is never substituted for a missing origin. Override the field lists when the actual exported schema requires it; `TenantId` is often the workspace ID and must not be assumed to be the originating Entra tenant.

The configured `SigninLogs` routes use case-insensitive `contains` on `UserPrincipalName`. For exact identity matching, replace `contains` with `eq` and use the full principal name. Multiple matching routes send copies to each destination. Before deployment, verify real workspace data-export messages contain the configured `Type`, `TimeGenerated`, and origin fields; a queryable workspace schema alone does not establish the export wire format.

To forward every record for a selected table/origin, omit its `filter` or use `null`. This does **not** forward records from other origins. Explicit fan-out to different workspaces is supported and incurs an ingestion charge for each copy.

Use the same origin kind and origin-field mappings for a source table across all routes. If multiple populated fields for the selected origin kind disagree, the record is quarantined. Records without an identifiable origin or with no configured origin/table route are also quarantined, never sent to a default workspace. An event that matches an origin/table route but fails its filter is **intentionally discarded**, not quarantined.

Input messages can be one JSON record, an array of records, or `{"records":[...]}`. Records require a string `Type` identifying the original table and a valid `TimeGenerated`. This project does not accept diagnostic-settings Event Hubs messages as an interchangeable source: their schemas require a separate adapter.

## Filters

Filters execute in the function, **not as KQL queries**. Field paths are case-sensitive and use dots for nested JSON objects; arrays and JSON-encoded strings are not automatically traversed/parsed.

```json
{
  "all": [
    { "field": "CategoryValue", "op": "eq", "value": "Administrative", "ignoreCase": true },
    {
      "any": [
        { "field": "ActivityStatusValue", "op": "eq", "value": "Failed" },
        { "field": "Level", "op": "in", "value": ["Error", "Critical"] }
      ]
    },
    { "not": { "field": "Caller", "op": "startsWith", "value": "test-" } }
  ]
}
```

- Groups: `all`, `any`, `not`. Exactly one group or leaf per filter.
- Leaves: `eq`, `ne`, `in`, `gt`, `ge`, `lt`, `le`, `contains`, `startsWith`, `endsWith`, `exists`.
- String comparisons are ordinal, case-sensitive unless `ignoreCase` is true.
- Ordering operators accept decimal numbers only; no string-to-number coercion.
- Missing fields fail leaf comparisons, including `ne`. `exists` distinguishes absence from explicit JSON `null`.
- `not` negates the entire child result, so `not` of a failed missing-field comparison is true. Combine with `exists` when absence should not pass.
- `exists` has no `value`. `in` requires a nonempty array. Groups have no `op`/`value`.
- Configuration rejects unknown properties/operators, duplicate origin/workspace/table combinations, conflicting table mappings, invalid endpoints/resource IDs, and source-workspace destinations.
- Filter trees are limited to 16 levels and 256 nodes.

## Destination schema

Native Azure tables cannot generally be populated by arbitrary reingestion. In particular, `AzureActivity` does not accept the Logs Ingestion API. Each selected source table therefore maps to a custom `_CL` table.

For each configured `sourceTable`, deployment reads the source table's column definitions (including standard columns) and creates a missing `targetTable` with the same non-generated column names and types. No schema is inferred from sample records. The DCR unwraps the original record into those top-level columns, preserving dynamic fields and converting scalar fields to their declared types. Router metadata and the `Payload` wrapper are used only in transit, not added to the destination schema.

Azure-managed columns (`TenantId`, `Type`, `_ItemId`, `_TimeReceived`, `_BilledSize`, `_IsBillable`, and `_SubscriptionId`) remain service-managed. They cannot be cloned as writable custom columns: `Type` identifies the destination table, `TenantId` identifies the destination workspace, and billing/ingestion metadata reflects the new ingestion. `_ResourceId` is projected when present in the source schema; Azure supplies its standard column. Thus the user-data schema matches the source, but Azure-managed metadata values and hidden system columns are not an exact replica. Columns declared as `guid` use `toguid()` in the DCR projection so the transform output matches the declared schema.

**Existing target tables are never deployed or updated.** Deployment reads and validates their non-generated column names/types; if they differ from the source, deployment stops before Azure changes and leaves the table unchanged. This includes tables created by the previous `Payload`-based router: select a new `targetTable` (and matching `streamName`) to adopt the source schema without modifying the old table. Compatible existing tables retain their schema, plan, retention, and data. New tables use the Analytics plan and workspace-default retention. Do not concurrently create/change target tables during deployment; existence/schema checks precede resource deployment.

The destination DCR checks the source workspace, source table, and configured origin allowlist **before** projecting source columns. Business filters are enforced by the function, not the DCR; grant ingestion permissions only to trusted identities.

Example destination query:

```kusto
ForwardedSigninLogs_CL
| project TimeGenerated, UserPrincipalName, AppDisplayName, ResultType
```

Log Analytics does not enforce uniqueness; delivery remains at least once. Use source-native event identifiers for query/application deduplication. The router's internal `DeliveryId` is not persisted as an extra destination column.

The router caps original records at 60,000 UTF-8 bytes to avoid transport-field truncation and caps requests at 900,000 bytes. Oversized records go to quarantine, never silent truncation. Large-event support requires a separately designed schema/storage strategy. Azure can normalize very old/future `TimeGenerated` values.


The deployment smoke test runs the real publish/configuration/ZIP workflow with a fail-closed mock Azure CLI; it never creates Azure resources. Run it with an absent `artifacts\publish` staging directory:

```powershell
.\tests\DeploymentSmoke.ps1
```

Its generated configuration/package contains mock endpoints and is **not** a production deployment. Archive/remove that specific staging directory before running a real deployment.

If nuget.org is inaccessible in your environment, Microsoft's public mirror can be used explicitly:

```powershell
dotnet test .\tests\LogRouter.Tests\LogRouter.Tests.csproj `
  -p:RestoreSources=https://pkgs.dev.azure.com/dnceng/public/_packaging/dotnet-public/nuget/v3/index.json
```

For local trigger execution, install Azure Functions Core Tools v4, copy `local.settings.example.json` to `local.settings.json`, supply actual resource values, and run `func start` in the function project directory. Authenticate with `az login`. Your developer identity needs Event Hubs Data Receiver, suitable host-storage blob permissions, failure-container write access, and Monitoring Metrics Publisher on the destination DCRs. Do not copy production credentials into local settings. The packaged configuration must match the configured Event Hubs namespace/name/group or startup fails.

The Functions host passes worker connection arguments when starting the executable. Normal startup accepts those arguments; only `--validate-config` and `--replay` are intercepted as maintenance commands. A successful ZIP deployment alone does not prove the worker is running: verify that Azure lists `RouteCentralLogs`, that Event Hubs checkpoints advance, and that destination records arrive.

The trigger normalizes Event Hubs metadata from raw AMQP annotations because the isolated-worker binding can supply string offsets and `DateTime` enqueue timestamps instead of the SDK's numeric offsets and `DateTimeOffset` timestamps. Both representations are supported; enqueue timestamps without a time-zone kind are interpreted as UTC.

## Deploy

The central and target Log Analytics workspaces must **already exist**. This deployment targets same-tenant subscriptions in Azure public cloud. It disables public network access on the Function App and Event Hubs namespace. The Function consumes events over Private Link using managed identity. The namespace still allows the trusted Microsoft services exception required by Log Analytics workspace export, which does not use the router's private endpoint. Storage and destination Logs Ingestion API access remain authenticated and are not made private by this deployment.

1. Copy the configuration to a working file and verify or replace source/target subscription IDs, workspace ARM IDs, origin IDs, DCR ARM IDs, table names, and filters. Keep syntactically valid placeholder DCR immutable IDs/endpoints until deployment replaces them.
2. Use **dedicated DCR names**: deployment manages the whole DCR. Choose custom destination names using `tables[].targetTable` and matching `streamName`. Existing tables are reused only if their non-generated schema matches; their settings and schema are never updated.
3. Use one DCR per target workspace, in that workspace's resource group. DCR region is set to the workspace region automatically.
4. Register `Microsoft.Insights`, `Microsoft.OperationalInsights`, `Microsoft.EventHub`, `Microsoft.Storage`, `Microsoft.ManagedIdentity`, and `Microsoft.Web` in the relevant subscriptions, plus `Microsoft.Network` and `Microsoft.App` in the router subscription. The central workspace region must support Flex Consumption, VNet integration, and .NET 10.
5. The deployer needs read access to all workspaces and their table schemas, rights to create missing tables and deploy resources in their resource groups, role-assignment write permission at the relevant scopes, permission to create the central data export and deploy Function code, and Azure Monitor's required Event Hubs export permissions on the selected namespace.
6. Start with a canary table/subscription policy before enabling full production volume.

```powershell
az login
.\scripts\Deploy.ps1 `
  -ConfigurationPath .\my-routing.json `
  -RouterResourceGroup rg-central-log-router `
  -NamePrefix central-router `
  -ThroughputUnits 12
```

On Linux, install .NET 10 SDK, PowerShell 7, Azure CLI, and Azure CLI Bicep; then sign in with `az login`. From the project directory, the prerequisite checker can verify the local tools and Azure CLI login:

```bash
bash scripts/check-linux-prerequisites.sh
```

If your Linux machine isn't connected to the router network yet, deploy central infrastructure first:

```bash
bash scripts/deploy-linux.sh \
  --configuration ./my-routing.json \
  --resource-group rg-central-log-router \
  --name-prefix central-router \
  --infrastructure-only
```

Then run the same command **without `--infrastructure-only`** from a Linux machine that can reach the Function App's private SCM endpoint. The PowerShell equivalent is `-InfrastructureOnly`. The first run creates central resources and disables the trigger but does not publish code or change destination resources or the workspace export rule. On an existing router, schedule these steps in a maintenance window: the trigger is disabled until the full deployment succeeds and public clients lose access.

### Networking options

Omit networking options to create a VNet with the current defaults. To override the IPv4 ranges for a **new VNet**, append options like these:

```bash
  --vnet-cidr '10.70.0.0/24' \
  --function-subnet-cidr '10.70.0.0/27' \
  --private-endpoint-subnet-cidr '10.70.0.32/28' \
  --jump-host-subnet-cidr '10.70.0.64/27'
```

In PowerShell, use `-VnetCidr`, `-FunctionSubnetCidr`, `-PrivateEndpointSubnetCidr`, and `-JumpHostSubnetCidr`. The defaults use the same subnet sizes and offsets under `10.250.0.0/24`. The jump-host subnet is created only when the VM is requested. Subnets must be inside the VNet and must not overlap. The new Function subnet is delegated to `Microsoft.App/environments` and gets a NAT Gateway and a public IP **for outbound connections only**; these resources incur charges.

To **reuse an existing VNet**, omit the CIDR options and append:

```bash
  --existing-vnet-id '<vnet-arm-resource-id>' \
  --existing-function-subnet-name 'snet-functions' \
  --existing-private-endpoint-subnet-name 'snet-private-endpoints'
```

Add `--existing-jump-host-subnet-name 'snet-jump'` if creating the optional VM. In PowerShell, use `-ExistingVnetId`, `-ExistingFunctionSubnetName`, `-ExistingPrivateEndpointSubnetName`, and `-ExistingJumpHostSubnetName`. The VNet may be in another resource group, but must be in the router subscription and source workspace region. Use distinct subnets: the Function subnet must already be delegated to `Microsoft.App/environments` with sufficient capacity (use `/27` or larger for one app), and the private endpoint and jump-host subnets must not be delegated. The deployment does not change the existing VNet address space, subnet configurations, or outbound routing. Ensure the Function subnet can reach its storage and Logs Ingestion API; ensure existing security rules allow the required private traffic and, if applicable, the VM's restricted RDP.

Use the same VNet and subnet settings in both deployment stages and on redeployments. The template links `privatelink.azurewebsites.net` (app and SCM) and `privatelink.servicebus.windows.net` (Event Hubs) to the chosen VNet. If it already uses private DNS zones for either suffix, coordinate with the network owner before deployment to avoid conflicting zone links. Connect the deployment machine to that network and verify the printed SCM hostname resolves to the Function's private endpoint IP. The script checks HTTPS reachability before uploading and never opens public access.

Optional arguments are `--subscription-id`, `--existing-eventhub-namespace`, `--throughput-units`, and `--nuget-source`. Configuration paths may be absolute or relative to the project directory. The script does not install software or change the Azure CLI's selected subscription.

### Optional Windows jump host

To create a public Windows Server 2022 jump host in the router VNet, register `Microsoft.Compute` in the router subscription. For username/password authentication without Key Vault, append these options to the `--infrastructure-only` command above:

```bash
  --jump-host-rdp-source-ip '<your-public-IPv4-address>' \
  --jump-host-admin-username 'routeradmin'
```

The script prompts for the Windows password without echoing it, and sends it to Azure Resource Manager over HTTPS as a secure deployment parameter. It does not write the password to a file or pass it on a command line. In PowerShell, use `-JumpHostRdpSourceIp` and `-JumpHostAdminUsername`. For automation, pass a `SecureString` to `-JumpHostAdminPassword` from an existing PowerShell session instead of using the prompt. Do not mix a direct password with the Key Vault options.

Alternatively, append the following options to use an existing Key Vault:

```bash
  --jump-host-rdp-source-ip '<your-public-IPv4-address>' \
  --jump-host-password-vault-id '<key-vault-ARM-resource-id>' \
  --jump-host-password-secret-name '<password-secret-name>'
```

In PowerShell, use `-JumpHostRdpSourceIp`, `-JumpHostPasswordVaultId`, and `-JumpHostPasswordSecretName`. Put a strong Windows administrator password in that existing Key Vault before deployment, enable **Azure Resource Manager for template deployment** on the vault, and grant the deployer `Microsoft.KeyVault/vaults/deploy/action` there. The parameter file contains a Key Vault reference, not the password. Use only a vault approved for this access.

The VM has a static public IP and allows inbound TCP 3389 only from your specified IPv4 address (`/32`). It uses the jump-host subnet described above and can resolve the private Function SCM and Event Hubs names. RDP to the printed address with the selected username (default `routeradmin` in Key Vault mode), then install PowerShell 7, .NET 10 SDK, Azure CLI with Bicep, and copy or clone the project and routing configuration onto the VM. Sign in with `az login` and rerun the PowerShell deployment command from the VM without `-InfrastructureOnly` or the jump-host RDP and credential options. Keep the same router configuration, resource group, name prefix, subscription, network settings, and Event Hubs namespace selection. The Function App and Event Hubs remain private.

Omitting the jump-host options on later runs leaves the existing VM in place. The VM, public IP, and OS disk can incur charges; remove the jump-host resources when no longer needed.

### Namespace and deployment scope

If needed, supply `-NuGetSource` with the mirror URL shown above. The script explicitly scopes every Azure command to its subscription; it does not change your default subscription.

`-RouterSubscriptionId` selects the subscription for the Event Hubs namespace, Event Hub, consumer group, managed identity, storage, plan, and Function. It defaults to the central workspace subscription. `-RouterResourceGroup` selects their resource group in that subscription; the resources are deployed in the central workspace's region. The source export rule remains in the source workspace's resource group, and destination DCRs and tables remain in their workspace resource groups. All subscriptions must belong to the same Entra tenant.

To reuse the existing IPAM test namespace instead of creating a namespace, run from the project directory:

```powershell
.\scripts\Deploy.ps1 `
  -ConfigurationPath .\src\LogRouter\routing.json `
  -RouterSubscriptionId '48f1a68c-cd48-430c-af15-b176f81fc22d' `
  -RouterResourceGroup 'rg-law-test' `
  -ExistingEventHubNamespaceName 'ehlr-law-test-b0525cd5' `
  -NamePrefix 'signin-router'
```

For the separate synthetic test workspace, use `-ConfigurationPath .\src\LogRouter\routing.synthetic-test.json` with the same placement arguments. This uses `SyntheticSigninLogs_CL`, not the native `SigninLogs` table. After the export rule is deployed and activated, create new test records:

```powershell
.\scripts\Send-TestSigninLogs.ps1 `
  -SubscriptionId '48f1a68c-cd48-430c-af15-b176f81fc22d' `
  -ResourceGroup 'rg-law-test'
```

The sender needs the Monitoring Metrics Publisher role on `dcr-synthetic-signins`. Records created before the export rule is active are not backfilled. The test workspace and DCR are dedicated test resources, not copies of production Sentinel or its native sign-in data. Verify export and destination queries after deployment; synthetic table behavior does not prove that the native `SigninLogs` export format is identical.

The existing namespace must be in the selected router resource group and the central workspace region, be ready and Standard or Premium tier, and have local authorization enabled. **Use a dedicated namespace:** the deployment replaces its firewall rules with a default deny and the trusted-services exception, creates a private endpoint, and disables public access. It does not change the SKU or throughput; `-ThroughputUnits` applies only when creating a new Standard namespace. The deployer needs permissions to change namespace networking, create private endpoints and DNS, and join the Function integration subnet. The Event Hub and consumer group are managed by the deployment; if the Event Hub already exists, it must have 32 partitions and 7-day retention. The `eventHubNamespace` value in the input JSON does not select an existing namespace by itself.

Deployment sequence:

1. Publish locally and validate routing configuration before making Azure changes.
2. Check workspace access, matching resource IDs, shared DCR selection, same-tenant subscriptions, source schemas, and compatibility of existing target tables.
3. Configure the private router infrastructure in the central workspace region and check that the deployment machine can reach the Function's private SCM endpoint.
4. Keep the trigger disabled while creating missing spoke tables from source schemas, provisioning each Direct-kind DCR, and assigning scoped Monitoring Metrics Publisher roles. Existing tables are excluded from table deployment.
5. Add DCR transformations that enforce source-workspace, source-table, and allowed subscription or tenant origin boundaries, then project the original fields into the destination schema. Per-table JSON business filters still run centrally.
6. Write resolved routing configuration to `artifacts\routing.deployed.json`, include it in the application ZIP, deploy code, and enable the trigger.
7. Create/update the central workspace export rule `central-spoke-router`, exporting the **union of all selected source tables** to the dedicated Event Hub.

Deployment can incur Azure charges immediately. No subscription resources are provisioned merely by building the project. Resource provisioning is not transactional: if a deployment fails, inspect the explicit error and existing resources before resuming. Do not remove existing Event Hubs/storage to recover; that can destroy pending records.

For redeployment, archive/remove only the specific `artifacts\publish` staging directory first; the script refuses to reuse it to prevent stale package files. Use the same `NamePrefix`, router subscription, router resource group, and namespace selection for stable infrastructure names. Redeployment temporarily disables the trigger while refreshing its package; Event Hubs retains the backlog. Changing the router location or namespace does not migrate queued records or delete old resources, and may create a second router; plan the cutover explicitly. Removing a route stops new delivery but does not delete old tables, DCRs, role assignments, failure blobs, or data. Review retired access and retention explicitly.

The deployment uses managed identity for Function storage, Event Hubs consumption, quarantine, and cross-subscription ingestion. No account keys or client secrets are embedded. Event Hubs local authorization remains enabled because Azure Monitor workspace export uses shared-access authorization.

## Failure handling and replay

- HTTP 408, 429, 5xx, network failures, and request timeouts are retried up to four total attempts.
- `Retry-After` is honored up to 30 seconds; longer delays are deferred to quarantine for later replay.
- Permanent HTTP ingestion errors and exhausted delivery retries are saved as `FailedDelivery/<hash>.json`.
- Malformed messages and invalid/unmapped records are saved under separate failure kinds.
- Identical failure blobs are not overwritten. If persistence fails, the invocation fails and the Event Hubs trigger retries indefinitely before checkpointing.
- Authentication failures outside the HTTP request also fail the invocation; fix identity/RBAC and allow the trigger to retry.
- Successfully quarantined batches allow other spokes to continue. Failed persistence or authentication can block a partition until repaired.
- A host retry or ambiguous network outcome can duplicate already-accepted deliveries. Delivery is **at least once**, not exactly once.
- Quarantine is not an automatic dead-letter queue or replay scheduler. An operator must monitor it and replay after fixing the underlying issue.

To replay an individual failed-delivery blob:

```powershell
az storage blob download --auth-mode login `
  --account-name <router-storage-account> --container-name quarantine `
  --name FailedDelivery/<hash>.json --file .\failure.json

dotnet .\artifacts\publish\LogRouter.dll --replay `
  .\artifacts\routing.deployed.json .\failure.json
```

Replay uses the **current** routing allowlist, origin checks, and filters, and re-creates the destination records from their original `Payload`. It refuses batches that are no longer permitted or no longer correspond to a configured target/stream. It does not automatically delete the failure blob. Verify successful destination ingestion before archiving/removing that exact blob. Replaying a batch twice can create duplicates. Malformed/unmapped records require investigation and manual correction, not blind replay.

## Production acceptance and sizing

The project is not load-certified for 600 GB/day or 400 million records/day. The 12-throughput-unit/32-partition defaults are an initial configuration, **not a capacity guarantee**. In particular:

- Measure actual exported JSON size, event packing, peak traffic, destination distribution, and projected record size. The transport envelope adds overhead even though router metadata is not stored in destination columns.
- A partition is the scale-out unit for this trigger; 32 partitions cap useful event-consumer parallelism even though the app permits more instances.
- A bounded dictionary lookup selects origin/table routes without scanning every subscription for every record.
- Function invocations batch Event Hubs messages, group accepted records by destination/stream, and batch ingestion requests by byte size. Sparse destinations produce smaller requests; `maxParallelDeliveries` bounds concurrency per invocation, not globally.
- Check current Logs Ingestion API limits **per destination DCR**, plus Event Hubs limits and Functions regional subscription quotas.
- Alert on export failures, Event Hubs throttling/consumer lag, Function errors/retries, quarantine growth, storage failures, and per-spoke freshness/count mismatches. Configure centralized log collection for console/host logs before production. This template does not deploy an alerting/observability stack.
- Quarantine can become very expensive if tables include many origins that have no routes. Estimate this separately and either configure those origins or deliberately redesign unmatched-record handling with audited discard policies. The implementation defaults to retention rather than silent loss.
- Azure Monitor data export has its own retry/discard window; seven days of Event Hubs retention only protects data that reached Event Hubs. Historical central data is not backfilled automatically.
- Validate table export support before enabling a table. One shared export rule avoids a rule per spoke, but workspace data-export rule quotas and source-table restrictions still apply.
- If a spoke workspace also exports these custom tables into the same pipeline, it can create a loop. The router forbids the central workspace as a destination; operators must also avoid indirect export loops.

Acceptance procedure:

1. Use synthetic records from two origins with overlapping table names and known include/exclude cases.
2. Verify each spoke receives only its allowed origin/table/filter matches, with original payload/time preserved.
3. Confirm malformed JSON, unknown origins, conflicting origin IDs, and oversized records appear in quarantine.
4. Deny a canary DCR's ingestion permission; verify failures are visible and durable and other spokes still receive records.
5. Restore permission, replay a failure, and verify destination rows using `DeliveryId`.
6. Exercise a quarantine-storage outage; verify the affected partition does not checkpoint past undurable failures.
7. Load-test sustained and burst traffic, measure consumer lag/ingestion limits, and reconcile source/export/destination counts with explicit filtered, quarantined, and duplicate categories.
